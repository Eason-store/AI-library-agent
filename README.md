# 图书馆借阅助手（Library Agent）

在多轮对话里完成 **查馆藏 → 判断可借 → 借书 / 续借 / 归还 / 预约** 完整闭环的图书馆助手。

大模型负责理解意图和把结果说成人话；**业务规则和数据都在服务端**；
馆藏检索用 Hybrid（BM25 + 向量 + RRF 融合）；网页端先登录、再对话，带按读者隔离的历史会话列表。

## 功能一览

- **登录注册**：读者注册 / 登录（JWT），前端按登录身份区分会话；密码加盐哈希存储
- **对话**：多轮上下文（保留最近 8 轮）、会话持久化（刷新页面 / 重启前端都不丢历史）
- **办理**：借书 / 还书 / 续借 / 预约，每个动作都封装成**固化的 skill**，大模型一次调用完成
- **查询**：按主题或书名检索馆藏、查某本书的可借状态与在架位置
- **状态**：每次调用模型前注入 Status Bar（当前读者、借阅额度、逾期情况、在借明细）
- **安全**：用户输入用固定分隔符包裹、system prompt 明确拒绝越权与套取规则、关键动作必须走工具
- **前端**：Streamlit 网页，登录页 + 左侧会话列表 + 右侧对话区

## 系统架构

```
Streamlit 前端（app/streamlit_app.py，端口 8501）
  │
  ├─ 登录 / 注册 / 取当前读者  →  LMS 后端 /auth/*  → 拿到 JWT token
  │                             （前端靠 token 记住"当前是谁"）
  │
  └─ 对话流程：
       ① 组装 messages（system + Status Bar + 检索上下文 + 历史）
       ② 调用大模型（DeepSeek API）
       ③ 模型要求调用工具时 → MCP 服务（8765）→ LMS 后端（8000）
                                                    │
                                                    ▼
                                    data/lms.sqlite（馆藏 / 读者 / 借阅 / 预约）
```

MCP 服务里暴露 6 个原子工具；agent 层另外封装了 5 个 skill（把"还书"这类流程固化下来）。

另外两条独立的数据链：

```
rag/    → 向量索引在 data/chroma_db（书名+作者+简介 做 Embedding）
agent/  → 对话历史在 data/chat_sessions.sqlite，工具调用轨迹在 data/traces/
```

**为什么工具放在 MCP 服务里而不是写成普通的 Python 函数**：让大模型根据自然语言自己判断
该调哪个工具，而不是由代码写死调用哪个接口 —— 这是 MCP 与普通 REST API 的核心区别。

## 快速开始

```bash
# 1. 安装依赖（Python 3.13）
pip install -r requirements.txt

# 2. 配置环境变量：在项目根目录建 .env（已在 .gitignore 里，不会被提交）
#    DEEPSEEK_API_KEY=sk-你的密钥        ← 必填
#    JWT_SECRET=一串随机字符             ← 可选；不写就用演示默认值

# 3. 灌测试数据 + 建向量索引（各约 10 秒；seed 要算密码哈希，会稍慢一点）
python -m lms.seed
python -m rag.build_index

# 4. 一条命令启动三个服务（LMS 后端 + MCP 服务 + Streamlit 前端）
python start.py
```

启动后：

```
接口文档（Swagger）  http://127.0.0.1:8000/docs
MCP 服务             http://127.0.0.1:8765/mcp
前端页面             http://localhost:8501
```

**演示账号**：借书证号 `R2025001`，密码 `123456`
（`seed.py` 给 50 个种子读者都设了这个统一密码；也可以在登录页注册一个新读者，注册时可以选等级）

> 首次启动 MCP 服务要加载向量模型，约 15 秒，`start.py` 会自动等待。
> 如果手工启动 MCP 服务（不走 `start.py`），记得先设 `HF_HUB_OFFLINE=1`，
> 否则它会去 HuggingFace 检查模型更新，断网时会卡好几分钟。

## 核心设计（几个值得说明的取舍）

1. **MCP 工具是原子操作，skill 是标准流程**
   6 个 MCP 工具一次只做一件事（借出一本、还掉一条）；5 个 skill 把"还书"这类流程固化：
   内部自动把书名换成借阅编号、再调工具，模型只需一次调用，不必每次自己串联步骤。

2. **检索有两条路**：规则化预检索（命中"查书"关键词时先检索，把结果作为上下文）
   + 工具式检索（模型觉得需要时自己调 `search_books`）。前者稳定省往返，后者灵活。

3. **Status Bar 每轮刷新**：调用模型前重新取一次读者状态并注入 system 消息，
   "已借 2/5 本""有 1 本逾期（按规定需先归还）"这些**结论由系统算好**，
   模型只负责转述 —— 业务规则的执行仍然在服务端。

4. **会话持久化 + 按读者隔离**：对话历史存 SQLite，前端的左侧列表直接读它，
   并且只显示当前登录读者的会话；刷新页面、重启前端历史都在。

5. **Prompt Injection 防御三层**：输入包 `<user_input>` 标签 + system prompt 明确拒绝
   + 关键动作必须走工具（不能因为读者说"就当我还了"就改状态）。

6. **评测可复现**：评测前自动重新灌数据、跑完再恢复；模型调用设 `temperature=0`
   （默认温度 1.0 会让同一条用例两次结果不同）。

7. **登录用 JWT，密码不存明文**
   `/auth/register` 和 `/auth/login` 校验通过后签发 JWT（token 里只放"是谁"和"过期时间"）；
   密码用标准库 PBKDF2（随机盐 + 十万次迭代）存成"盐$摘要"。
   前端每次页面重跑都调一次 `/auth/me`：既刷新侧栏的借阅状态，也顺便验证 token 是否还有效。

## 评测结果

```
检索评测（20 条检索用例，Recall@5）
  BM25   0.90
  向量   0.76
  融合   0.95      ← 融合优于两路单独，符合 Hybrid 检索的预期

端到端评测（20 条用例：正常 10 / 异常 6 / 注入 4）
  任务成功率      1.00  (20/20)
  工具调用正确率  1.00  (12/12，只统计要求调用工具的用例)
  注入拒绝率      1.00  (4/4)
```

**评测经历过三轮迭代**（过程和结论都保留在提交历史里）：

| 轮次 | 任务成功率 | 工具正确率 | 注入拒绝率 | 这一轮发现并修掉的问题 |
|---|---|---|---|---|
| 第 1 轮 | 0.85 | 0.77 | 1.00 | 1 条用例期望写错（预检索已完成检索，不该再要求模型调工具）；2 条 prompt 没落实"关键动作必须走工具" |
| 第 2 轮 | 0.95 | 1.00 | 0.75 | 暴露出 1 条注入用例偶发失败 |
| 第 3 轮 | 1.00 | 1.00 | 1.00 | 根因是大模型默认温度导致输出随机；设 `temperature=0` 后评测可复现 |

## 与项目文档的差异说明

1. `books` 表增加了 `description` 字段（文档表结构漏写，但向量检索需要"书名+作者+简介"）
2. 增加了一个接口 `GET /books/{id}/availability`（文档要求"至少覆盖"，`next_return_date` 只能服务端算）
3. 融合用 RRF（文档括号里明确允许），不是 `0.6*vector + 0.4*bm25`
4. 预约增加了"有在架副本时拒绝预约"的补充规则（文档未规定）
5. 预约 3 天失效用**惰性清理**（预约接口被调用时扫一遍），不是后台定时任务
6. `fine` 恒为 0（文档没有罚金条款，但工具返回值里要求这个字段）
7. 6 个工具写在 MCP 服务里（按导师要求，取代文档骨架的 `agent/tools.py`）
8. Status Bar 携带在借明细，替代文档样例对话里提到的 `get_user_loans`（它不在 6 个工具清单里）
9. 检索用例采用"规则标注"（每条查询配一条可审计的规则）；纯口语化意图查询在合成馆藏上无法客观标注
10. `users` 表增加了 `password_hash` 字段（登录模块需要；文档 3.1 的表结构里没有）
11. 增加了 `/auth/register`、`/auth/login`、`/auth/me` 三个接口（导师要求的登录模块，文档未规定）

## 已知局限

- **注册时可以自选读者等级**（普通 / 学生 / 教师）：方便演示三档额度（5 / 8 / 15 本）；
  真实系统里等级应由图书馆管理员授予，否则读者都选"教师"就能借 15 本。
- **接口级鉴权未做**：`/auth/me` 会校验 token，但借还等业务接口仍按文档签名接收 `user_id` / `loan_id`，
  没有强制校验"token 里的读者 == 请求里的读者"；当前依赖 system prompt 约束 + 服务端业务规则兜底。
- **登录态不持久化**：token 存在浏览器的会话状态里，关闭标签页或重启前端需要重新登录
  （要"记住我"得把 token 存进 cookie）。
- **JWT 密钥默认值是演示用的**：正式部署必须用环境变量 `JWT_SECRET` 传随机长字符串。
- **馆藏是合成数据**：`seed.py` 用固定随机种子生成 500 本书，只有前 15 本是真实书目。
- **RRF 稀释**：有 3 条检索用例上 BM25 全对、融合反而被稀释（已量化，见评测记录）。
- **未实现罚金**：逾期只影响能否继续借书。
